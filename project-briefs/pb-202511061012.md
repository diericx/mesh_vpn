### Project Overview

**Goal**: Create a decentralized mesh VPN built on WireGuard with simple usability and automatic NAT traversal.

**Technology Stack**:

- Language: Go (Golang)
- VPN Protocol: WireGuard (must be pre-installed on hosts)
- Firewall: iptables
- NAT Traversal: STUN (no TURN server initially)
- Target Platform: Linux only

### Architecture & Technical Requirements

#### Core Components

1. **WireGuard Management**

   - Manage WireGuard configuration files on each host
   - Handle peer addition/removal in WireGuard config
   - Manage WireGuard interface lifecycle

2. **Mesh Orchestration Protocol (UDP)**

   - Separate UDP port for mesh communication (distinct from WireGuard traffic)
   - Dynamic discovery of nodes with open/forwarded ports
   - Peer-to-peer communication for key exchange and network topology updates

3. **STUN NAT Traversal**

   - Built-in STUN server functionality
   - Automatic broker selection (nodes with open ports)
   - Dynamic connection establishment between NAT'd peers

4. **Access Control Lists (ACLs)**

   - Per-node ACL configuration file
   - Defines inbound/outbound network access per peer
   - Enforced via iptables rules

5. **Firewall Management**
   - Automatic iptables rule creation/deletion
   - Default deny policy (connections locked until explicitly allowed)
   - Separate rules for incoming and outgoing traffic per peer

#### Network Architecture

- **Dual UDP Communication**:
  - WireGuard traffic: Standard WireGuard UDP port (configurable)
  - Mesh orchestration: Separate UDP port (e.g., 4949)
- **Port Discovery**:
  - Nodes dynamically detect which peers have publicly accessible ports
  - This information is shared across the mesh
  - Used to select STUN brokers for NAT traversal

#### Configuration & State Management

- **Node Identification**: Human-readable names (e.g., "S1", "S2", "S3")
- **Persistent Storage**: Local configuration files for:
  - Known peers (name, public IP, WireGuard public key, port status)
  - ACL rules (per-peer allow/deny for incoming/outgoing)
  - WireGuard interface configuration

### User story

A user has three linux servers, named S1, S2 and S3. They have installed this vpn software on each machine. S1 will be our communication broker and thus will have a UDP port forwarded for the orchestration API (4949 for example). The servers will manage each other via these human readable names like "S1", "S2", etc. in the command line and in their configs. The servers will have IPs of `24.156.199.1`, `24.156.199.2`, and so on.

The user adds S2 to S1 via command line [1]. Keys are exchanged, wireguard connections are setup, and now S1 and S2 are aware of each other and have saved info in the ACL config file, but the network is locked at the firewall level (iptables) such that neither can communicate with each other yet. S2 allows all networking to and from S1 via command line. S1 allows does the same. [2] There is now an open wireguard connection between the two.

Now we want to give S3 access to the network. S3 adds S1 as it is the only server it can communicate with at the moment [3]. They both allow all networking with each other. S3 can now view the the full available network using the command line [4]. S3 then adds s2. This communication requires STUN traversal since s2 and s3 cannot see each other. They both know that S1 has an open port, so they use S1 as the stun broker. Once a connection is made, they transfer keys and setup wireguard connections. This connection, and any required new connections if they were to go offline for an extended period of time, is kept alive and managed through S1. S1 is chosen as the broker simply because it is known to be an open server via its open port. Which server exactly is used is arbitrary.

[1] `s2:$ mvpn add S1 24.156.199.1`

[2] `s2:$ mvpn allow incoming S1`
`s2:$ mvpn allow outgoing S1`
`s1:$ mvpn allow incoming S2`
`s1:$ mvpn allow outgoing S2`

[3] `s3:$ mvpn add s1 24.156.199.1`

[4]

### Bug Fix - Ubuntu 24.04 iptables Issue (2025-11-06)

**Issue**: On Ubuntu 24.04, daemon failed to start with error:

```
Error: failed to start daemon: failed to initialize firewall: failed to link OUTPUT chain: failed to add jump rule: exit status 2
```

**Root Cause**: The [`ensureJumpRule()`](internal/firewall/iptables.go:64) function in [`internal/firewall/iptables.go`](internal/firewall/iptables.go:1) was incorrectly using `-i` (input interface) flag for all iptables chains including OUTPUT. The OUTPUT chain requires `-o` (output interface) flag instead.

**Fix Applied**: Modified [`ensureJumpRule()`](internal/firewall/iptables.go:64) to dynamically select the correct interface flag based on the chain type:

- INPUT and FORWARD chains: use `-i` (input interface)
- OUTPUT chain: use `-o` (output interface)

### Bug Fix - Port Conflict Issue (2025-11-06)

**Issue**: After fixing the iptables issue, daemon failed to start with error:

```
Error: failed to start daemon: failed to start STUN server: failed to start STUN server: listen udp 0.0.0.0:4949: bind: address already in use
```

**Root Cause**: Both the mesh protocol ([`internal/mesh/protocol.go`](internal/mesh/protocol.go:1)) and STUN server ([`internal/stun/stun.go`](internal/stun/stun.go:1)) were trying to bind to the same UDP port (4949), causing a port conflict.

**Fix Applied**: Refactored the architecture so that:

1. Only the mesh protocol creates and manages the UDP listener on port 4949
2. STUN server registers its message handlers with the mesh protocol instead of creating its own listener
3. Both components share the same UDP connection
4. Created a `MessageProtocol` interface in STUN to allow dependency injection
5. Moved `MessageHandler` type to [`internal/types/types.go`](internal/types/types.go:8) for shared use
